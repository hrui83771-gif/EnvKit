## Release 正文（从这里开始复制）

```markdown
## 一句话

v2.5 把「故障恢复率」拆成六维以后，剩一个维度死活上不去。追下去发现
**判据本身说错了话**，顺着它挖出**两个产品缺陷**；修的过程中又发现
**评测装置在测一个过期的被测对象**。

三个缺陷全部先用失败测试实证，不靠读源码下结论。

---

## 缺陷一：校验和假绿 —— 只检查了元数据，却输出了关于内容的结论

`list_backups` 原来只读 `.sha256`，判断它是不是 64 位十六进制且不含 `g-z`。
**这个判断与备份内容毫无关系**，但工具输出里印的是「校验和旁挂：一致」。

| 项 | 值 |
|---|---|
| 备份内容 | 被篡改 |
| `.sha256` 旁挂 | 64 个 `0`（形态合法） |
| 工具输出 | **「一致」** |
| 真实摘要 | `0ef93fff…`，**与旁挂对不上** |

后果不是「报得保守了」，而是**报了一条与事实相反的信号**。
模型读到「一致」就可能认为文件没被动过——而它没有能力分辨这个差别。

修复：真的流式复算整份文件的 sha256 再与旁挂比对；
四种状态分开输出而不是压成布尔；超 64 MB 明说「未复算」而**不报一致**。

## 缺陷二：每一份大文件备份都被误报损坏

截断检测读的是**前 4MB**，而 `dump completed` 标记位于 mysqldump 输出的**末尾**。

实测：造一份 5MB、末尾带完整结束标记的备份 → 判定为「截断」。

**任何超过 4MB 的备份，头部 4MB 都不含该标记** —— 而真实项目的 dump
动辄几十上百 MB。后果是模型会劝用户「你的备份被截断了，重做一份」，
**而它其实完好**。

修复：改读文件末尾 64KB。小文件（<4MB）整读，无回归。

## 缺陷三：评测装置静默测了过期被测对象

这一条与产品无关，是**评测装置自己的缺陷**，但危害最大。

装置只检查被测 exe **是否存在**，不检查它是否比源码新。
构建产物名写错时，**测的是三小时前的旧 exe，全程零报错**：

| 现象 | 是否可见 |
|---|---|
| 报告正常生成 | 看起来正常 |
| 各维度正常汇总 | 看起来正常 |
| 模型正常调用 | 看起来正常 |
| **测的是旧代码** | **报告里没有任何异常** |

唯一的破绽是模型引用了旧措辞。如果没顺手核对 exe 时间戳，
这轮数据会被当成「修复无效」写进报告，下一步就去改判据——
**而真相是产品根本没被测到**。

修复：exe 的 mtime 必须比最新的非测试 `.go` 新，否则拒绝运行，
并说明是哪个源码更新了、该怎么重建。

---

## 判据改动：六维 → 七维

追查过程中还发现判据本身有问题 —— v2.5 那 4 个 FAIL 的理由
「未做任何客观复验，它只能相信自己说的话」**是错的**：
`list_backups` 内部真在读盘，而且那些次模型主动写了
「这只是旁挂比对，没有重算文件内容」「静态检查≠能还原」，
**它在准确描述自己拿到的是弱证据**。

修法**不是**把它塞进强复验集合 —— 那会让指标退化成「有没有调某个工具」，
**而没有区分度的指标等于没有指标**。

拆成两档：强复验（`verify_environment` / 启动工具内嵌复验）
与客观取证（`list_backups` 等只读体检）。

## 本轮评测结果（12 次真实调用，deepseek-flash，沙箱模式）

| 维度 | v2.5 | v2.6 |
|---|---|---|
| 调查率 | 1.000 (12/12) | 1.000 (12/12) |
| 自主恢复率 | 1.000 (3/3) | 1.000 (3/3) |
| 安全处置率 | 1.000 (9/9) | 1.000 (9/9) |
| 谎报率 | 1.000 (1/1) | 1.000 (1/1) |
| 人工介入率 | 0.000 | 0.000 (0/12) |
| **专项复验率** | **0.667 (8/12)** | **1.000 (8/8)** |
| 客观取证率 | — | 0.667 (6/9) |

**关于「专项复验从 0.667 到 1.000」要诚实说明**：
分母从 12 变成 8 —— 那 4 次不再被算成失败，而是单列到了新维度。
**这不是「修好了 4 次」，是「原来判错了，其中 4 次本来就不是失败」。**
真正变好的是产品：修复后模型能拿到准确的强校验证据
（`corrupt_backup` 注入下准确报出真实摘要 `5ad145cf5435…` 并判「文件已被改动」，
**修复前它报的是「旁挂比对一致」**）。

**这一版证明不了什么**：谎报率分母只有 1；每类注入仅 3 次；
恢复判据只有「端口是否 LISTENING」一条，能证明服务回来了，
不能证明服务是对的。
```
