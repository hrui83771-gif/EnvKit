# EnvKit v3.0 UI 设计稿

> 目标：把「功能按钮集合」改造成「项目状态中心」。
> 原则：**收紧入口，不收紧能力；AI 增强本地能力，而不是取代本地能力。**
>
> 本文所有现状结论均锚到源码（文件:行号），复核方式见附录 A。

---

## 零、本稿的定位

> **交互原型**：[`preview-v3ui.html`](preview-v3ui.html)（浏览器直接打开）
> 可切换工作区、切换状态灯规则、查看设计说明。用真实字段与真实数据渲染。
> 其中首页有一个开关能把「绿灯只看 running」的旧规则切回来，用来看清 v3.0 改掉了什么。

v2.2 已经交付了统一状态源 `/api/runtime/state`（`runtime.go:88`），但**前端一次都没接**——
`web/index.html` 中 `"/api/runtime/state"` 出现次数为 0，`issues` 字段被引用 0 次。

这意味着 v3.0 的 UI 重构**不是纯前端改版**，而是要把已交付但闲置的能力接上，
并顺带消灭三套并存的轮询。这是本稿第一优先的原因。

| | 规划里的假设 | 实际情况 |
|---|---|---|
| Runtime 状态源 | 已就绪，UI 可直接用 | 服务端就绪，**前端零接入** |
| 前端状态计算 | 需收敛为统一来源 | **三套轮询并存**：`pollHealth` / `pollState` / `pollProg` |
| 面板数 | 5 个 | **6 个**（`install` 的容器 class 与其余五个不同，故按 `class="panel"` 统计会漏） |

## 一、现状盘点

### 1.1 界面规模与结构（实测）

```
web/index.html          4,174 行 / 252 KB（单文件内嵌）
导航项                       6 个：install / config / chain / start / ai / audit
面板容器                     6 个：panel-install / panel-config / panel-chain /
                                panel-start / panel-ai / panel-audit
内联 JS                     3,255 行（1 个 script 块）
fetch 调用                  32 处，涉及 25 个 API 端点
```

**入口已经是 6 个，不算少。** 那"太密集"的感觉来自哪里？——不是数量，
是**首页承担了太多互不相关的职责**，且**状态在 6 个页面里各算各的**。

### 1.2 三套轮询各算什么（`web/index.html`）

| 函数 | 数据源 | 算什么 | 频率 |
|---|---|---|---|
| `pollHealth`（2821 行） | `/api/health` | 顶部 5 个状态芯片、侧栏状态点、权限标识 | 持续 |
| `pollState` | `/api/state` | 组件检测结果与版本 | 持续 |
| `pollProg` | `/api/program/state` | 启停进度 | 任务执行期间 |

问题不在"三套"这个数字，而在**同一件事被算了两遍**：

```
pollHealth 里：
  const svcOk = h.services.web.running || h.services.backend.running;   ← 服务状态
  chip('chip-deps', depsOk?'ok':'warn', ...)                            ← 依赖状态
  chip('chip-env', ...)                                                 ← 环境状态

而 /api/runtime/state 已经把 env / deps / services / db / chain / issues 全算了，
且 services 里还有 pollHealth 用不到的 phase / verified / restarts / last_err。
```

**结论**：状态计算的唯一来源已经存在，UI 仍在用旧的三套并行。
v3.0 的第一步不是改版式，是**把状态源接上**。

### 1.3 「太密集」的真实成因（逐条锚源码）

| # | 症状 | 源码依据 | 用户感受 |
|---|---|---|---|
| 1 | 首页承担安装、检测、配置、启动、日志五件事 | `panel-install` 内含检测按钮链；`panel-start` 内含 6 个启停按钮 | 打开就是一大屏按钮 |
| 2 | 同一状态在多处重复呈现 | 顶部 5 芯片 + 侧栏状态点 + 各面板内又算一遍 | 扫一眼不知道哪个是真的 |
| 3 | 「有什么问题」没有统一答案 | 前端从未消费 `issues`（0 次引用） | 只能自己逐页找 |
| 4 | 服务状态只有"跑着/没跑" | 前端只用 `running` 布尔，忽略 `phase`/`verified` | 进程在跑但没验过时也显示绿灯 |
| 5 | 出错后不知道该做什么 | 前端无 issue 列表 | 只能读日志猜 |

**第 4 条最严重**：`ServiceState.Phase` 有五态（`stopped/starting/running/degraded/failed`），
`runtime.go` 特意把「进程在跑但没复验过」标为 `degraded`——
**这就是「执行不等于成功」在状态灯上的体现，而 UI 完全没显示出来**。

## 二、设计原则（不可违反的硬约束）

| # | 原则 | 验收方式 |
|---|---|---|
| 1 | **不删能力**：现有 25 个前端调用的 API 端点、6 个面板的功能项，重构后一个都不能失去可达性 | 逐条列映射表（§5.3） |
| 2 | **状态唯一来源**：所有状态灯、状态文字、健康结论来自 `/api/runtime/state` | 代码审查：前端不得出现第二处状态推断逻辑 |
| 3 | **AI 可用性无关**：AI 未配置 / 未启用 / 密钥失效时，首页与全部工作区功能完整 | 断网 + 清空 AI 配置的 CDP 场景 |
| 4 | **手动优先**：手动按钮不经过 AI、不依赖记忆开关 | 手动路径的调用链里不得出现 AI 模块 |
| 5 | **问题带出路**：每条 issue 必须展示 `action` 字段，不允许只报错不给下一步 | 渲染层测试：issue 缺 action 时必须显式提示 |
| 6 | **不新增入口**：工作区数量固定为 5，导航项不超过 7（含首页） | 导航项计数断言 |

## 三、信息架构

### 3.1 结构

```
首页  状态            现状 / 问题 / 最近动作 —— 只回答"现在怎样"
├ 运行  Run            启停、重启、进程管理、端口诊断
├ 诊断  Diagnose       健康检查、日志、链端诊断、诊断报告
├ 数据  Data           数据库、备份、还原、SQL、数据浏览
├ 助手  Agent          对话、任务轨迹、记忆与经验、操作审计
└ 设置  Settings       组件安装、项目配置、链端配置、AI 配置
```

### 3.2 现有 6 个面板的归属（含迁移理由）

| 现有面板 | 去向 | 理由 |
|---|---|---|
| `install`（环境安装） | **设置** → 组件 | 安装是配置行为，不是日常操作。且它体量最大（含镜像加速、SHA256 校验、演练安装），压成设置区的一个折叠块 |
| `config`（程序配置） | **设置** → 项目/链端/AI | 已经是配置形态，只是与其他配置混在一个页面 |
| `chain`（链端运维） | **诊断** → 链端 | 用户去链端页的两种动机：查状态（属首页/诊断）、做操作（端口扫描、重启、SSH 终端）。前者不需要进链端页 |
| `start`（程序启动） | **运行** | 主体直接对应 |
| `ai`（AI 助手） | **助手** | 主体直接对应 |
| `audit`（操作审计） | **助手** → 审计页 | 审计与记忆/经验同属"Agent 干了什么"，放一起才看得出因果 |

**净变化**：导航 6 → 6（新增"首页"、移除无实际价值的顶层项），但每个工作区内部**按任务分组**，
不再是一屏铺开。

### 3.3 设置区的分组（解决"设置也太长"）

```
设置
├ 组件            安装 / 版本 / 缺失组件          ← 原 install 面板
├ 项目            目录 / 启动方式 / 数据库名
├ 链端            SSH / 端口 / 守护开关
└ AI              服务商 / 密钥 / 模型 / 记忆开关
```

每组独立折叠，**默认全部折叠**。理由：配置是"改一次用很久"的操作，
不该每次打开都占满屏。

## 四、首页 = 状态中心

### 4.1 布局

```
┌──────────────────────────────────────────────────────────────┐
│  FarmTrace                          [全部启动] [全部停止]     │
│  ● 有 1 个问题需要处理                          上次更新 3s 前  │
├───────────────┬───────────────┬──────────────────────────────┤
│ 前端          │ 后端          │ 数据库                        │
│ ● 运行         │ ● 运行         │ ● 已连接                      │
│ :8080 · 2h14m │ :8888 · 45s   │ farm · 12 张表                 │
│ [重启] [停止] │ [重启] [停止] │ [备份] [浏览]                 │
├───────────────┴───────────────┴──────────────────────────────┤
│ 链端          ● 节点存活    块 1105 · 交易 1355 · 节点进程 4   │
│ 依赖          ⚠ 待办 1 项   磁盘 42% · 内存 3.2G              │
├──────────────────────────────────────────────────────────────┤
│ ⚠ 前端依赖未安装（node_modules 缺失）                        │
│   → 先执行 npm install，否则 npm run 必然失败      [去处理]   │
├──────────────────────────────────────────────────────────────┤
│ 最近  前端已启动 45s 前 · 备份完成 2h 前 · 复验通过 5s 前      │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 状态灯语义（全局统一，四色）

| 色 | 含义 | 数据来源 |
|---|---|---|
| 🟢 绿 | 已就绪：运行**且**已复验通过 | `phase == running && verified` |
| 🟡 黄 | 降级：在跑但未复验 / 有待办项 | `phase == degraded`，或 `issues` 里有 warn |
| 🔴 红 | 失败 | `phase == failed`，或 `issues` 里有 error |
| ⚪ 灰 | 停止 | `phase == stopped` |

**关键**：绿色要求 `verified`。`runtime.go` 特意把「进程在跑但没复验」标为
`degraded`，UI 必须照实显示为黄色——**这是整份设计稿最重要的一条**：
把"执行不等于成功"落到界面上，否则前面所有验证层的努力在视觉上等于零。

### 4.3 卡片与数据的对应关系（逐字段）

| 卡片 | 显示项 | 字段 |
|---|---|---|
| 前端/后端 | 状态灯 | `services.web.phase` + `verified` |
| | 端口 | `services.web.port` |
| | 运行时长 | `services.web.uptime_sec` |
| | 连续失败 | `services.web.restarts`（>0 时显示） |
| | 退避建议 | `services.web.backoff`（连续失败 ≥3 次时显示） |
| | 最近复验 | `services.web.last_verify`（hover 显示全文） |
| | 崩溃历史 | `services.web.crashes[]`（最近 3 条，折叠展示） |
| 数据库 | 连接 | `db.connected` + `db.dbExists`（**camelCase**） |
| | 版本 / 最近检测 | `db.version` / `db.at` |
| 链端 | 状态 | `chain.checked` + `port20200` + `webaseOk` |
| | 块高/交易数 | `chain.blockNumber` / `chain.txCount`（**均为字符串**） |
| | 节点进程数 | `chain.nodeProcs`（-1 = 未知/未探测） |
| | 最近自动恢复 | `chain.lastRecover` |
| 依赖 | 就绪/待办 | `deps` + `project.web_deps_installed` |
| 问题区 | 逐条 | `issues[].level/scope/what/action` |

> **实现必读的坑**：`RuntimeState` 内部**命名风格不统一**——
> `services` / `db` / `env` / `issues` 是 snake_case（`uptime_sec`、`last_verify`），
> 但嵌进来的 `ChainInfo`（`chain.go:53`）是 camelCase（`blockNumber`、`port20200`、`webaseOk`）。
> 前端取值时不要凭直觉写，**照抄 JSON tag**。P1 落地时若发现这是设计失误，
> 应在 Runtime 层统一命名而不是在前端做兼容映射——兼容映射等于把不一致永久固化。

### 4.4 问题区（首页最重要的部分）

**每条必须渲染 `action`**，且带一个"去处理"入口跳到对应工作区。

分级呈现：`error` 在最上，其次 `warn`，`info` 收进折叠。

理由：`Issue.Action` 是后端算好的可执行下一步（`runtime.go` 里每条 issue 都带），
前端丢掉它等于把负担推回给用户——而"给不出下一步的告警等于噪音"。

## 五、迁移与实现

### 5.1 分三批，每批可独立验收

| 批 | 内容 | 验收标准 | 风险 |
|---|---|---|---|
| **P1** | 接入状态源：新建 `rtStore` 单例，`pollHealth` 改为读它，删掉重复计算 | `/api/runtime/state` 被调用；`pollHealth` 里不再出现状态推断（只剩渲染） | 低。响应字段已存在，格式不变 |
| **P2** | 首页状态中心：新面板 + 侧栏首个入口 | 断掉 AI 后首页功能完整；问题区显示真实 issue | 中。新增视图，但不改旧面板 |
| **P3** | 工作区重组与设置分组 | 25 个 API 端点的可达性逐条核对通过 | 高。涉及大量 DOM 搬移 |

**顺序不能倒**：P2 依赖 P1（没有统一状态源就做首页，等于又多一套计算）；
P3 依赖 P2（先验证状态中心好用，再把其它页面收进去）。

### 5.2 前端状态管理的最小实现

```js
// rtStore —— 唯一状态源的前端镜像
// 设计要点：只有一处能把 RuntimeState 变成 DOM，其余模块只读它。
const rtStore = (()=>{
  let cur = null;                 // 最近一次 RuntimeState
  const subs = [];                // 订阅者
  const timer = { id: 0, ms: 3000, ok: false };
  async function pull(){
    if(busyNow) return;           // 任务执行期不轮询，避免与任务抢状态
    try{
      const r = await fetch('/api/runtime/state');
      if(r.ok){ cur = await r.json(); ok = true; emit(); }
    }catch(e){ ok = false; }
  }
  return {
    get: ()=>cur,
    sub: f=>subs.push(f),
    start(){ if(!timer.id) timer.id = setInterval(pull, timer.ms); pull(); },
    stop(){ clearInterval(timer.id); timer.id = 0; },
    // 手动操作后立即刷新，不等下一个轮询周期
    // 理由：用户点了"启动"却要等 3 秒才看到状态变化，会以为没生效
    poke(){ pull(); }
  };
})();
```

三个刻意的取舍：

1. **任务执行期不轮询**——`busy` 时状态由任务自己上报，轮询只会抢状态且误导。
2. **`poke()` 而非纯轮询**——手动操作后立即刷新。这直接对应原则 4「手动优先」。
3. **`ok` 标志与"状态未知"分离**——拉取失败**不能**渲染成"一切正常"，
   而要显示"状态获取失败"。这与 v2.0 修掉的"AI 谎报成功"同源。

### 5.4 状态灯的渲染规则（伪码）

```js
function svcLamp(st){
  if(!st) return 'off';
  if(st.phase === 'failed') return 'err';
  if(st.phase === 'degraded') return 'warn';   // 在跑但没验过 —— 不能显示绿
  if(st.phase === 'running') return st.verified ? 'ok' : 'warn';
  if(st.phase === 'starting') return 'warn';
  return 'off';
}
```

`verified` 缺失时按 `false` 处理——**不确定时显示"未验证"而不是"正常"**。
这与链端判据（无交易时块高静止属正常但视图在推进）、
守护状态（未跑第一轮时说"尚未完成第一轮检测"而非"正常"）是同一条纪律。

## 六、验收标准

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 前端状态推断逻辑只有一处 | 代码审查：除 `rtStore` 外不得有 `phase`/`verified` 判断 |
| 2 | 25 个 API 端点全部可达 | 逐条点击核对，写入测试清单 |
| 3 | AI 完全不可用时功能完整 | CDP：清空 AI 配置 → 启停/备份/复验/诊断全部可执行 |
| 4 | 状态灯语义正确 | 构造 `degraded` 状态 → 断言显示黄色**而非**绿色 |
| 5 | 问题区每条都有出路 | 断言每条 issue 的 action 非空且可点 |
| 6 | 导航项 ≤ 7 | 计数断言 |
| 7 | 无状态源时显示"获取失败" | 断网 → 断言不显示"一切正常" |
| 8 | CDP 现有 14 套全绿 | 回归 |

## 七、明确不做

| 不做 | 理由 |
|---|---|
| 删除任何现有功能 | 原则 1。改版式不等于减能力 |
| 首页做成一键操作台 | 那正是"太密集"的成因。首页只回答"现在怎样" |
| 用 WebSocket 替代轮询 | SSE 已有（`/api/events`）用于日志；状态是低频变化，轮询够用且更简单。**不引入新的实时通道** |
| 引入前端框架 | 单文件内嵌是分发优势（`make_dist` 产物只有 exe + bat + 说明）。引入框架会破坏零依赖打包 |
| 主题/配色重做 | 与本目标无关，且用户未提出 |
| 移动端适配 | 桌面运维工具，优先级低 |

## 附录 A：现状结论的复核方式
