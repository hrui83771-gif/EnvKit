## 一、对话里弹「AI 服务返回错误：http: read on closed response body」

这行红字**不是上游出错**，是我们自己关掉连接后，又把自己关的动作当成了上游故障上报。

流程是这样的：

1. 上游发完 `data: [DONE]`，主循环 `break` 跳出读取循环；
2. 收尾时 `resp.Body.Close()` 去叫醒还卡在 `sc.Scan()` 里的读取 goroutine；
3. 那个 goroutine 拿到 `http.ErrBodyReadAfterClose`，写进 `readErr`；
4. 主循环只看 `readErr != nil`，于是弹了「AI 服务返回错误」——而这轮回复其实**完整收到了**。

判断依据不是推测：`body.closed` 这个标志**只由本地 `Close()` 设置**，上游断连只会给 EOF / reset，永远造不出这条错误。`ai_abort_test.go` 里用 `httptest` 把这个因果复现了一遍（`TestCloseAfterDoneProducesBodyReadAfterClose`）：服务端发完 `[DONE]` 但不关连接，客户端读完就 `Close`，扫描方拿到的正是这条错误。先红后绿验证过：把判据删掉该用例就红。

改动三处：

| 位置 | 改动 |
|---|---|
| `ai_loop.go` | 新增 `sawDone`：收到 `[DONE]` 之后不再采信 `readErr`；定性抽成 `aiUpstreamReadErr(readErr, sawDone)` |
| `aiIsAbortErr` | 白名单加 `read on closed response body`——这条错误 `errors.Is` 判不出来（类型中途被包过），只能比文本 |
| 收尾 | 加 `<-scanDone`，等扫描 goroutine 真退出再读 `readErr`，顺手消掉一个跨 goroutine 的数据竞争 |

**没有放宽中断判定**：真正的上游错误（EOF、502、读超时）照旧弹红。

## 二、压缩历史太频繁

日志实证：

```
21:06:03  已生成对话摘要（压缩 30 条 → 710 字）
21:06:52  已生成对话摘要（压缩 36 条 → 704 字）   ← 49 秒后又来一发
21:09:54  已生成对话摘要（压缩 42 条 → 739 字）
```

算得出来为什么：压完之后历史水位 = `keepTokens 3000` + 摘要约 400 ≈ **3400 token**，而触发阈值只有 **5000**，只剩 1600 余量；`cut` 每次前进 6 条消息，攒几下就又跨过去。于是每几十秒重打一次十几秒的前置调用——体感就是「老在压缩」。

三处改动：

| 改动 | 说明 |
|---|---|
| `summary_after_tokens` 5000 → **10000** | 压完水位降到 34%，余量约 6600 token ≈ 4~6 轮工具调用。默认值与已生成的 `config.json` 同步 |
| 摘要失败加 **5 分钟负缓存** | 原来失败后每回合都重试（10-27 日志有一次「空响应」），每回合白等一次最长 60s 的前置调用——体感同样是「老在压缩」 |
| 旧摘要不再当「用户发言」喂回 | 原来会压出「用户：（系统注入的此前对话要点备忘…<untrusted_data>…」这种自指嵌套；现在单独作为「已有要点」交给模型合并 |

提示文案也从「一次性，约十几秒」改成「只压这一轮，约十几秒」——「一次性」容易被读成「一辈子只压一次」。

对模型侧协议没有改动：摘要依然是 `role=user` 的一条系统备忘（模型侧要认这个结构），改的只是**构造时不再把上一条备忘当成用户说过的话**。

## 三、桌宠天气：勾了不生效 / 霾天飘英文 / 细节看不见

三个问题各有各的原因：

**勾了不生效。** 原来只有点「应用」按钮才写盘，勾选框本身只是个本地状态。现在勾上即时保存，并通过 `BroadcastChannel('ek-pet-cfg')`（+ `localStorage` storage 事件兜底）广播到其它窗口，多开也一致。「保存基础设置」也会一并保存。

顺带修了一个隐形的数据破坏：没填过城市时提交空串，会把已存的「合肥」改成默认「上海」。现在前端用 `ekWeatherCityLoaded` 标记「用户真的改过这个字段」，没改就不带该字段；后端对应字段是 `*string`，缺省即不动。

**霾天飘英文。** 旧实现把 `wttr.in` 的英文描述按**文本**查词表，而实测 16 个城市返回的描述只有 11 种，最常见的 `149 Smoky haze`、`152 Smog` 两个词表里都没有，于是原文漏到界面（`113 Clear/Sunny` 也会漏）。现在改为**按 `weatherCode` 查表**（113~395），文本查表只作后备。`TestWeatherCodeTableIsComplete` 把实测到的类型逐条钉住。

**细节看不见。** 天气接口原本只透传温度与描述；现在补上体感、湿度、风向风速、能见度，气泡里分三行显示，并附一句建议（带伞 / 防晒 / 少开窗）。设置页天气卡片顶部新增一行状态，显示服务端实际生效的城市。

## 四、喂食挡住她说话

食物栏原来是横排、悬在头顶，展开时正好压住气泡。现在改成**贴侧面两列**，并且加了兜底：食物栏与气泡矩形若相交，气泡自动上移。

顺带修了一处几何量取错误：气泡夹取边界时量的是 `getBoundingClientRect()`，而元素正处于 scale 过渡中，量到的是缩小版，实际显示会越界 8px。改用 `offsetWidth` 的布局宽度计算。

## 五、闭环接缝测试与评测装置

v3.6.0 修的三处「结论报错」都发生在**模块之间的接缝**上，而当时所有单测都是绿的。这版补上了正面覆盖：

- `agent_loop_e2e_test.go`：一条测试串起七段——告警 → pending → 执行+复验 → done → 存为预案 → 再存被拒 → 同类告警命中（起草 Draft 而 Plan 为空）→ done + 统计 → 连败 3 次转 `review` → 经验召回。不调模型，确定性 0.3s。变异验证过：把 `Draft` 落盘抽掉、把 `pbkSettle` 短路，用例必红。
- 修 `missionFromGuard` 返回值说谎：命中预案后返回的仍是套预案前的副本，调用方拿到的是「空预案」，与落盘不一致。
- 评测题 T15/T16 **第一次真跑**：T16 PASS 3.3s；T15 PASS×3 各约 610s。过程中修掉评测装置三处「把对判成错」——空正文被当成采集失败（其实是确认卡停留的正常行为）、判据只认正文不认确认卡、报告按题覆盖写导致 T16 冲掉 T15。

**一处未定性的异常，如实记在这里**：真实 HTTP 下用事件流里的 `tool_call_id` 去 POST `/api/ai/confirm`（`approved:false`）会 30s/60 次全部 404 `no_waiter`，而进程内直接投递 0.19s 就能成功。原因没查清，所以 T15 仍按超时收口，不假装它能被拒。

## 六、升级说明

直接覆盖 `EnvKit.exe` 即可，配置与数据（`config.json` / `missions.json` / `playbooks.json` / `memories.json` / 审计）都在 exe 同目录，不受影响。

两点需要注意：

- **摘要阈值改了默认值**，但你 `config.json` 里如果已有显式值，会继续用你的值（不会覆盖）。嫌吵就去设置页「开发者配置 → 摘要触发阈值」拉大，上限 32000。
- 桌宠天气的城市若显示不对，在设置页重新选一次即可；旧配置里的城市不会被默认值顶掉。
