# EnvKit 长期规划：v2.1 → v3

> 从「AI + 工具集合」到结构统一的 **Agent Runtime**。
>
> 分支：`v3`（长期开发分支，逐版本推进，每版打 tag）
> 基点：`6eae5c7`（v2.0.0 + 启动方式推断）
> 文档状态： living plan，随代码事实修订

---

## 零、现状盘点

结论全部锚到源码，可复核。

### 0.1 主链路八个环节的成熟度

目标链路：`Observe → Understand → Plan → Policy → Execute → Verify → Audit → Learn`

| 环节 | 现状 | 缺口 |
|---|---|---|
| Observe | 组件检测、端口扫描、进程统计（`detect.go` / `portscan.go`） | 只看"装没装"，不看"配得对不对"（无环境适配性判断） |
| Understand | `projectBrief`（项目画像）+ `aiHealthSnapshot`（环境快照） | **两个独立事实源**，字段不互通，AI 要自己拼；无"决策事实层"概念 |
| Plan | **不存在**。AI 直接调工具，无显式计划、无依赖序、无回滚 | 无法回答"你打算怎么做""做失败了怎么退" |
| Policy | 确认闸门（428）+ AI 白名单 + 高危标记 | **三处分散**、语义不一致；"危险"没有统一判据 |
| Execute | 任务函数返回 `OpResult`（`opresult.go`） | 部分路径仍返回裸 `error`；`StartSpec` 不存在（脚本/入口/目录散在参数里） |
| Verify | 三个验证器：service / backup / chain（`verify.go` 693 行） | 不覆盖进程生命周期（崩溃重启、僵尸、端口漂移）；无 HTTP 健康端点探测 |
| Audit | 完整（`audit.go`，JSONL，30 天，含 verify 字段） | 无"审计的审计"；无跨会话操作链追踪 |
| Learn | `lesson.go` + `memory.go`（本次新增） | 无 Scope / Confidence / 失效 / 冲突机制；经验不可纠正 |

### 0.2 规模与结构

```
代码      14,259 行 Go / 47 文件 + 4,079 行单文件前端
API       68 个路由
工具      17 个（环境 5 / 探索 3 / 服务 4 / 数据 2 / 验证 1 / 记忆 2）
界面      5 个面板（配置 / 链端 / 启动 / AI / 审计）
测试      156 项单测 + 13 套 CDP + 14 项端到端 AI 验收
最大单文件 ai_loop.go 1054 行、chain.go 885 行、program.go 788 行
```

### 0.3 三个结构性问题

1. **事实源分裂**：`projectBrief` 说"项目是什么"，`aiHealthSnapshot` 说"环境怎么样"，`chainInfo` 说"链端如何"，三者无一致性约束。AI 拿到的是拼图，不是事实。
2. **执行语义不统一**：同样是"启动前端"，按钮路径、AI 路径、批量启动路径的校验与返回语义各不相同。
3. **UI 与能力脱节**：功能已经很多（68 路由），但首页仍是"功能按钮集合"——新增能力只能继续堆按钮。

## 一、版本路线

| 版本 | 主题 | 核心交付 | 分支 |
|---|---|---|---|
| **v2.1** | 决策事实层 + **评测基线** | ProjectBrief 升级为 `DecisionFact`；`StartSpec` 统一执行输入；生命周期验证；**八项指标口径 + 基线 + 冒烟集 10 题** | `v3` |
| **v2.2** | Agent Runtime 收拢 | `Plan` 层落地；PolicyGate 四档；服务状态机；健康检查扩展 | `v3` |
| **v2.3** | 学习闭环 | 经验机制化（Scope/Confidence/失效/冲突）；Memory 安全边界 | `v3` |

## 二、v2.1：决策事实层

> 目标：让"这个项目该怎么跑"成为**系统事实**，而不是每次靠推断、靠猜、靠用户口头告知。

### 2.1 已完成（`6eae5c7`）

- 启动脚本从 `package.json` 推断（白名单 ∩ 非黑名单），危险脚本剔除并可见
- 后端入口从项目结构推断（`main.go` → `cmd/*/main.go`），识别不出则明确失败
- 用户可在配置页覆盖，留空=自动推断
- AI 快照新增 `launch` / `launch_plan` 字段

### 2.2 待做：ProjectBrief → DecisionFact

**问题**：现在 `projectBrief` 是"项目摘要"，只描述项目；决策需要的却是"在这个项目 + 这个环境 + 这些约束下，该怎么做"。

**方案**：新增 `DecisionFact`，把"事实"与"推断"分开，每条都带来源与置信度。

```go
type DecisionFact struct {
    Key      string   // "web.launch_script"
    Value    string   // "serve"
    Source   string   // config | package.json | probe | infer | user
    Conf     float64  // 0~1，probe/config 为 1，infer 按规则衰减
    Stale    bool     // 项目文件 mtime 变化后置位，需重算
    Evidence string   // 依据摘要（路径/行号/命令）
}
```

关键约束：

- **事实与推断物理隔离**：`Source=infer` 的项不得直接用于执行，必须先经 Policy 确认或用户确认。
- **失效机制**：项目文件（package.json / go.mod / 目录结构）mtime 变化 → 相关事实标记 `Stale` → 启动前强制重算。用过期事实启动服务是隐蔽的事故源。
- **一致性校验**：`DecisionFact` 与 `aiHealthSnapshot` 冲突时以 `DecisionFact` 为准（它更接近项目），并记一条冲突日志。

### 2.3 待做：StartSpec 统一执行输入

现在"启动前端"的输入散在三个地方：HTTP body 的 `dir`/`script`、AI 工具的 `service` 参数、localStorage 收藏。三条路径的校验强度不同。

```go
type StartSpec struct {
    Target    string   // web | backend
    Dir       string   // 绝对路径，须在允许根内
    Command   string   // 由 DecisionFact 解析得出，非直接采信
    Source    string   // 决策来源，用于审计
    Conf      float64
}
```

所有启动路径（按钮 / AI / 批量 / 未来 CLI）统一走 `StartSpec` → Policy → Execute → Verify，不允许旁路。

### 2.4 待做：进程生命周期验证

现有 `verifyService` 只验"端口在监听"。真实故障场景：

| 场景 | 现有验证 | 需要补 |
|---|---|---|
| 服务启动后 30 秒崩溃 | 验不到（端口曾监听过） | 存活观察窗（默认 10s）+ 崩溃捕获 |
| 端口漂移（配置改了但没生效） | 只能验预期端口 | 实际监听端口 vs 预期端口，不符即报 |
| 僵尸进程（父进程退出、子进程残留） | 验不到 | 进程树孤儿检测 |
| 服务反复重启 | 验不到 | 重启计数与退避策略状态 |

**验收标准**：构造"启动即崩溃"的服务，验证器必须报失败并附崩溃日志尾部，而不是报成功。

## 三、v2.2：Agent Runtime 收拢

> 目标：八个环节用同一套类型契约串起来，让"AI 声称成功也不等于事实成功"成为结构性保证，而非提示词里的君子协定。

### 3.1 Plan 层：从"直接调工具"到"有计划"

现状：AI 收到"帮我把项目跑起来"，直接调 `start_service(all)`。多步骤任务（"先装依赖再启动再验证"）没有显式编排，全靠模型临场决定。

方案：引入轻量 `Plan`，不搞通用规划器，只做**可核查的步骤序列**。

```go
type PlanStep struct {
    ID       string
    Action   string   // 工具名或本地动作
    Args     map[string]any
    Depends  []string // 前置步骤
    Rollback string   // 失败时的回退动作（可空）
    Expect   string   // 期望达成的可验证状态
}
type Plan struct {
    Goal    string
    Steps   []PlanStep
    Unknown []string // 明确"我不知道"的点 → 必须问用户，不许猜
}
```

规则：

- `Plan.Unknown` 非空时，AI **必须先问用户**，不许用猜测填坑。这是"承认无知"的结构化表达。
- `Expect` 必须是可验证的（端口、文件哈希、视图推进），不能是"服务正常"这种无法证伪的描述。
- 回滚不是强制的，但破坏性步骤必须有。

### 3.2 Policy 统一：把三处判定合成一处

现状三套判定：AI 工具白名单（`opt-in`）、HTTP 428 确认、高危红框标记。它们各自维护、各自演进，导致"什么算危险"没有单一答案。

方案：`PolicyGate` 统一裁决，输出**四档**而非布尔：

| 档位 | 含义 | 例子 |
|---|---|---|
| `auto` | 可直接执行 | 读日志、看状态 |
| `confirm` | 需用户确认 | 启停服务、备份 |
| `elevated` | 需确认 + 明示风险 + 建议先备份 | 还原数据库、改配置 |
| `forbidden` | 拒绝执行，AI 不可绕 | 删除数据、危险脚本 |

**核心规则**：`Memory` 不是权限，`Lesson` 不绕过 Policy。这条要写成代码级断言，不能只写在提示词里——经验命中时只能**调整建议顺序**，不能提升档位。

### 3.3 服务状态机

现状：`svcState["web"].running` 是布尔值，表达不了"启动中""降级""反复重启"。

```go
type ServiceState struct {
    Phase   string   // stopped | starting | running | degraded | failed
    PID     int
    Since   time.Time
    Restarts int      // 本次周期内重启次数
    Backoff string   // 退避策略状态
    LastErr string
    LastVerify time.Time
}
```

有了状态机，"服务到底怎么样"才有唯一答案，UI 与 AI 看到的是同一份事实。

### 3.4 健康检查扩展

| 检查项 | 判据 | 现有 |
|---|---|---|
| 端口监听 | netstat + 进程归属 | ✅ |
| HTTP 握手 | GET/HEAD 响应码与头 | ✅ |
| 端口漂移 | 实际监听 vs 预期 | ❌ 新增 |
| 存活观察 | N 秒后仍在 | ❌ 新增 |
| 崩溃检测 | 退出码 + 日志尾部 | ❌ 新增 |
| 数据库连通 | 真实 SELECT 1 + 库存在 | ✅ |
| 备份可还原 | 校验和 + 尾部完整 | ⚠️ 只验文件，未验可还原 |
| 链端活性 | 共识视图推进 | ✅ |

### 3.5 备份可还原性验证（重要缺口）

现状：备份验到"SHA256 一致 + 尾部完整"就认为成功。**但文件没坏 ≠ 能还原。**

方案：可选的深度验证——把备份导入临时库并跑一次 schema 校验（不覆盖真实库）。这是"备份能用来救命"的唯一证明。

代价：需要临时库权限与时间。设计为**用户显式触发的深度操作**，不进自动流程。

## 四、v2.3：学习闭环

> 目标：不是"积累越来越多的记忆"，而是"**在环境变化时知道旧经验已经不可信**"。

### 4.1 经验机制化

当前 `Lesson` 只有 `Kind/Title/Trigger/Hits/Evidence/Enabled`。补齐：

| 字段 | 作用 | 例子 |
|---|---|---|
| `Scope` | 适用边界 | 项目路径 + 环境指纹（OS/组件版本/数据库版本） |
| `Confidence` | 置信度，随成败计数衰减/增长 | 3 次成功 1 次失败 → 0.75 |
| `SuccessCount` / `FailureCount` | 成败计数 | 决定 Confidence 与是否降权 |
| `Lifecycle` | 生命周期状态 | active → stale（项目变了）→ retired（长期未命中） |
| `Conflict` | 与哪条经验冲突 | 新证据与旧结论矛盾时标记双方待裁决 |

**失效规则**（这是"会重新判断"的关键）：

1. 项目指纹变化（依赖版本、目录结构、组件版本）→ 命中该 Scope 的经验降为 `stale`，注入时降权到 0.3
2. 同一 Action 连续失败 2 次 → 该经验 Confidence 直接归零并标记 `retired`
3. 环境指纹不匹配 → 不注入（而不是降权）

### 4.2 经验纠正：允许被证伪

现状经验一旦生成，正向证据不会让它更新。需要：

- 每次相关操作后，对命中的经验做**成败结算**（成功 +1，失败 -1）
- 允许用户直接"标记这条经验是错的"，进入 `retired` 并记审计
- 新经验与旧经验矛盾时（如"该用 serve"vs"该用 dev"）不静默覆盖，而是标记冲突并按 Confidence 高者注入，另一条降权

### 4.3 安全边界（写成可测断言）

| 边界 | 实现方式 | 测试 |
|---|---|---|
| Memory 不是权限 | 记忆只影响建议顺序，`PolicyGate` 档位不受记忆影响 | 单元测试：注入"跳过确认"的记忆，档位仍为 confirm |
| Lesson 不绕过 Policy | 经验命中不提升档位 | 同上 |
| 历史状态不冒充当前 | 所有事实带 `Stale` 标记，启动前强制重算 | 集成测试：改 package.json 后旧经验不参与决策 |
| 经验不来自 AI 总结 | 提取全部走确定性规则 | 已满足（`extractLessons` 无模型调用），保持 |

### 4.4 验收标准

构造实验：让 AI 在同一项目上跑 10 次"启动服务"，第 6 次手动改错启动脚本，观察：

- 前 5 次：经验被正确命中，AI 直接采用
- 第 6 次起：旧经验被标记 `stale`/降权，AI 重新读 package.json 并发现变化
- 全程无"AI 坚持用过时经验导致重复失败"

## 五、v3.0：仪表盘化 UI

> 原则：**收紧入口，不收紧能力。AI 增强本地能力，而不是取代本地能力。**
>
> 形态：**本地 Runtime 是底座、AI 是上层驾驶员、UI 是仪表盘、用户始终拥有手动驾驶权。**

### 5.1 现状问题

5 个面板承载 68 个 API 路由。新增能力只能继续堆按钮或堆面板，首页逐渐变成"功能按钮集合"——用户找不到"我现在该看什么"。

### 5.2 目标结构

```
首页（Status）           项目状态中心：实体卡片 + 状态灯 + 核心控制
├ 运行（Run）            启停 / 重启 / 进程管理 / 端口诊断
├ 诊断（Diagnose）       健康检查 / 日志 / 链端诊断 / 诊断报告
├ 数据（Data）           数据库 / 备份 / 还原 / SQL / 数据浏览
├ Agent                 对话 / 任务 / 记忆与经验 / 操作审计
└ 设置（Settings）       组件 / 项目配置 / 链端配置 / AI 配置
```

### 5.3 首页设计：项目状态中心

以**实体**组织，而非以**功能**组织：

```
┌─────────────────────────────────────────────────┐
│  FarmTrace                          [ 全部启动 ]  │
├──────────────────┬──────────────────┬───────────┤
│  前端             │  后端             │  数据库    │
│  ● 运行中        │  ● 运行中        │  ● 已连接  │
│  :8080 · 2h14m   │  :8888 · 45s     │  farm     │
│  [重启] [停止]   │  [重启] [停止]   │  [备份]   │
├──────────────────┴──────────────────┴───────────┤
│  链端  ● 共识推进中   块 1105   视图 869701      │
│  依赖  ● 就绪         磁盘 42%   内存 3.2G       │
├─────────────────────────────────────────────────┤
│  最近事件：前端已启动 45s 前 · 备份完成 2h 前     │
│  ⚠ 1 条经验已失效（项目依赖变更）                │
└─────────────────────────────────────────────────┘
```

要点：

- 每张卡片的**状态必须来自 `DecisionFact` 与 `ServiceState`**，不是各页面自己算的
- 手动控制按钮**直接可用**，不经过 AI
- AI 不可用时，首页与所有工作区**功能完整**（这是硬要求）
- 状态灯语义全局统一：绿=健康、黄=降级/未验证、红=失败、灰=停止

### 5.4 手动驾驶权保障

| 保证 | 实现 |
|---|---|
| 所有 AI 能做的，手动都能做 | 手动路径不依赖 AI 配置，不受记忆开关影响 |
| 手动操作与 AI 操作同等留痕 | 审计 actor 区分 user / ai，字段结构一致 |
| 手动可覆盖 AI 的判断 | 配置页可锁定启动方式等关键项，AI 不得覆盖 |
| AI 不可用时系统完整 | AI 模块故障不影响 Runtime（已在 v2.0 验证） |

## 六、评测与证明

> 目标不是"功能更多"，而是能**客观证明比上一版更强**。

### 6.0 评测先行：现在就该做的与不该做的

**用户提问"评测是不是要先建"——答案是要，但不能理解成"先把 40 道题出完"。**

不先建评测的代价很具体：v2.0 就出现过"感觉变好了"却无法证明的困境（真实 bug 靠 e2e 偶然撞出来，而不是被指标挡住）。但一次性建全量集同样是浪费——**任务集必须锚定已存在的能力**，v2.2 才有 PolicyGate，现在根本测不了它。

拆成三件事，按紧迫度：

| 优先级 | 做什么 | 为什么现在做 |
|---|---|---|
| **P0** | **定义八项指标的精确口径**（只定义，不取数） | 口径不统一，后续所有数据不可比。这是纯文档工作，零成本 |
| **P0** | **跑一次基线**（当前 v2.0+v2.1 状态） | 不测基线，v3.1 拿什么证明"比上一版强"？**这比出题更紧急** |
| **P1** | **冒烟集 10 题**，只覆盖已交付能力 | 随提交跑，防回归。题目来自已实现的功能，可立即写 |
| P2 | 全量集 40 题 + 自动化 Harness | v3.1 交付，届时按新增能力扩展 |

**基线现在就能测的**：启动推断正确性、验证层判据、经验提取准确率、越权拦截率。
**现在测不了、必须等版本的**：Plan 层合规率（v2.2）、经验增益（v2.3）、误拒率（v2.2 有 PolicyGate 才有意义）。

基线的作用不只是"有个数"——它会**立刻暴露**当前能力的最短板，决定 v2.2/v2.3 的优先级。

### 6.1 指标口径（先定，后续不可改）

| 指标 | 精确定义 | 采集来源 | 可测起点 |
|---|---|---|---|
| 任务成功率 | 完成 ground_truth 全部 criteria 的比例 | 端到端执行器 | **v2.1** |
| 首次成功率 | 第一次尝试即全部通过的比例 | 尝试计数 | **v2.1** |
| 故障恢复率 | 注入异常后自主恢复成功的比例 | 异常注入器 | **v2.1** |
| 无效操作次数 | 与目标无关的工具调用总数 | 审计流 | **v2.1** |
| 验证准确性 | 声称成功与客观事实一致的比例 | 对比 verify 与真实探测 | **v2.1** |
| 安全违规率 | 触碰 `forbidden` 边界的比例 | PolicyGate 日志 | v2.2 |
| 误拒率 | 合法操作被判 deny/confirm 的比例 | PolicyGate 日志 | v2.2 |
| 经验增益 | 有经验 vs 无经验的成功率差值 | A/B 对照 | v2.3 |

**"验证准确性"是 EnvKit 独有的指标**——别的项目测不了它，因为它正是本项目的主张。优先做深。

### 6.2 Evaluation Harness

```
eval/
  tasks/           任务定义（YAML，含 ground_truth 与 success_criteria）
  fixtures/        可复现的项目样本（不同技术栈/结构/异常）
  runner/          执行器（起环境 → 提任务 → 收结果 → 判分）
  metrics/         指标计算
  reports/         报告输出（入 docs/eval/）
```

任务集分六类：

| 类别 | 覆盖 |
|---|---|
| `env/` | 缺组件、版本不符、端口冲突 |
| `project/` | 多技术栈、非标目录、缺依赖 |
| `startup/` | npm run dev / serve / start、cmd 布局、启动即崩 |
| `db/` | 连不上、备份、还原、损坏 |
| `chain/` | 不可达、节点挂、WeBASE 异常 |
| `security/` | 越权读文件、危险脚本、Prompt 注入、越界删除 |

任务定义示例：

```yaml
id: startup-npm-dev-001
setup: 前端项目仅含 npm run dev
task: "帮我把服务起起来"
ground_truth:
  exec_command: "npm run dev"
  must_verify: [web]
  must_not: [npm run serve, 硬编码脚本]
success_criteria:
  - 服务在预期端口监听
  - verify_environment 返回已复验通过
  - AI 报告中不含未验证的成功声明
```

### 6.3 持续回归与发布闸门

- 每次提交跑**冒烟集**（10 题，<5 分钟）
- 每个版本跑**全量集**（40 题，出报告）
- **指标回退即阻断发布**：任一指标相对上一版本下降超过阈值，必须书面说明原因或回滚
- 报告入 `docs/eval/`，随版本归档
- **评测集本身要版本化**：旧集冻结，新能力只加新题，不改旧题（否则无法比较）

### 6.4 v3.0 发布时的验收凭证

- 全量任务集通过率报告
- 八项指标的版本对比曲线（v2.0 基线 / v2.2 / v2.3 / v3.0）
- 至少一个"经验带来增益"的量化对照实验
- 冒烟集纳入发布流水线（人工执行也算，但必须留记录）

## 七、系统基础能力专项

用户指出：这些是"之前迫于条件没做或可以再进一步"的。它们不是 v3 的配角，**是 Agent 能力的地基**。

| 能力 | 现状 | 缺口 | 计划 |
|---|---|---|---|
| **环境识别** | 装没装 + 版本号 | 不判"配得对不对" | 需求符合性检查：项目要求 Node ≥16 但装的是 14 → 明确报不匹配；`v2.2` |
| **进程管理** | Job Object 回收 | 无孤儿检测、无进程树可视化 | 进程树视图 + 孤儿清理；`v2.2` |
| **服务生命周期** | start/stop/restart 三态 | 无崩溃重启策略、无退避 | 状态机 + 指数退避 + 重启上限；`v2.2` |
| **健康检查** | 3 个验证器 | 不覆盖漂移/存活/崩溃 | 扩到 8 项（见 3.4）；`v2.2` |
| **配置** | schema + 校验 | 无漂移检测 | 环境/项目变化后标记配置为待复核；`v2.1` 起 |
| **备份** | 校验和 + 尾部完整 | **未验可还原** | 深度验证（导入临时库）；`v2.2` |
| **审计** | 完整留痕 | 无跨会话操作链 | traceID 串联一次任务的多步操作；`v2.3` |
| **恢复** | 备份能验证 | 恢复流程不完整 | 一键恢复向导 + 恢复前强制预检；`v2.3` |
| **可观测性** | 实时日志 | 无历史趋势、无指标聚合 | 关键指标时序（启动耗时/失败率/复验通过率）；`v3.0` |

**优先级判断**：备份可还原性验证与环境符合性检查**优先做**——它们直接支撑"执行不等于成功"这个核心主张，其余可后置。

## 八、架构演进

### 8.1 类型收敛

```
现在：params 散落 + error + OpResult + verify 文本 + audit 字段   → 语义五份
目标：StartSpec / PlanStep / OpResult / Evidence / Verification   → 单一契约
```

统一后的一次动作只产生一条记录：

```go
type ActionRecord struct {
    TraceID  string       // 串联一次任务的多步
    Actor    string       // user | ai | guard | system
    Spec     StartSpec    // 意图
    Plan     []PlanStep   // 编排
    Result   OpResult     // 执行结果
    Evidence []Evidence   // 客观证据（端口/哈希/视图）
    Verify   Verification // 复验结论
    Lessons  []string     // 命中的经验
}
```

这条记录同时喂给：审计落盘、UI 展示、AI 上下文、经验提取、评测统计。**一份事实，五处使用**。

### 8.2 文件结构演进

现状（行数只是表象，**职责边界才是判据**）：

```
ai_loop.go       1054   7 种职责混在一起
chain.go          885   5 种职责 + 一个 200 行巨型函数
program.go        788   混入了与"启停"无关的 SQL 风险扫描 172 行
verify.go         693   3 个验证器共享 Evidence 构造，职责内聚
dbops.go          562   职责内聚
ai_tools.go       531   工具注册表，天然该集中
launch.go         304   职责单一 —— 同样是"不大但清晰"的好样板
```

**判据**：不是"超过 N 行就拆"，而是"这块是否正在改"。拆分的最优时机是**功能演进时顺手**，不是预防性重构——预防性重构会撞碎 v2.0 刚建立的测试网。

#### 优先级清单

| 文件 | 症状 | 拆法 | 时机 |
|---|---|---|---|
| `ai_loop.go` | **7 种职责**：SSE 写流 / HTTP handler / 意图判定 / 消息裁剪 / 滚动摘要 / 工具结果处理 / 质量检测，外加 300 行主循环 | `loop.go`（主循环）/ `stream.go`（SSE）/ `intent.go`（意图与回溯）/ `summary.go`（裁剪与摘要）/ `toolresult.go` | **v2.2 之前必须拆**。Plan 层要改的正是主循环，届时动它风险最大 |
| `program.go` | SQL 风险扫描 6 个函数 172 行与"启停"完全无关，属错位 | `sqlrisk.go`（扫描）+ `program.go` 只留启停 | **v2.1 顺手拆**（改动机械、可立即验证） |
| `chain.go` | 5 种职责：SSH / 可达性 / WeBASE / 恢复 / 守护；`doChainCheckWithRecover` 单函数约 200 行 | `chain_ssh.go` / `chain_probe.go`（可达性）/ `chain_webase.go` / `chain_recover.go`（恢复+守护） | **v2.2 拆**（与链诊断重构一起） |
| `verify.go` | 三个验证器共享 Evidence/OpResult 构造，拆开会引入跨文件耦合 | 随 v2.2 加状态机时统一重构为 `verify/` 包 | **v2.2**，届时一起动 |
| `dbops.go` | 职责内聚（建库/备份/还原/演练） | 不拆 | — |
| `ai_tools.go` | 工具定义集中便于一眼看全 | 不拆文件；可按类别分注册函数，表结构仍集中 | — |

原则：**新代码不再进 `ai_loop.go`**（它从 v2.0 起就是维护债重灾区），新文件按主链路环节命名。

### 8.3 一次动作一条记录

```
现在：params 散落 + error + OpResult + verify 文本 + audit 字段   → 语义五份
目标：StartSpec / PlanStep / OpResult / Evidence / Verification   → 单一契约
```

明确排除，避免范围蔓延：

- ❌ 自建 LLM 推理层（用现成模型 API）
- ❌ 通用工作流引擎（Plan 只做可核查的步骤序列）
- ❌ 多项目/多环境编排（当前是单项目本地工具）
- ❌ 自动修改用户配置（除非显式确认且可回滚）
- ❌ 把记忆做成权限来源（永远不是）

## 九、风险与取舍

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 大重构引入回归 | 高 | 高 | 每个版本独立发布独立回滚；`PolicyGate`/`DecisionFact` 收口时保留旧路径适配层 |
| UI 重构丢掉能力 | 中 | 高 | 首页只做**重组**不做删减；工作区收纳后逐项验收功能可达性 |
| 经验机制越复杂越不可用 | 中 | 中 | 机制分两批：先 Scope+Confidence，验证有效再上 Conflict |
| 评测集变成负担 | 中 | 中 | 分级：冒烟集 10 题随提交跑，全量集 40 题随版本跑 |
| 性能退化（快照越来越大） | 中 | 中 | 快照字段配额 + 分层注入；超限字段改为工具按需获取 |
| Python/工具链不稳定影响开发 | 已发生 | 中 | 已有兜底（见技能文档）；验收改用 Go 单测 + CDP，减少对 Python 脚本的依赖 |
