## 一、这一版基线要回答的问题

v2.2 基线第五节把 v2.3 的优先级排成六项，v2.3 全部交付。但有一件事没做：

> **v2.3 验收标准**：能出示「经验增益」的 A/B 对照数据——有经验组与无经验组
> 在真实任务上的对比。做不到这一点，学习闭环无法证伪。
>（`docs/ROADMAP.md` 第644 行）

九项都交付了，这一条没有。**更严重的是：v2.3 的九项能力在冒烟集里一题都没有。**
冒烟集停在 S01~S20，而 v2.3 新增能力**全部零命中**——在补题前的基点
`e949933` 上核对，`checkAllEnvReq` / `verifyBackupStatic` / `dbReadOnlySQL` /
`budgetFor` / `shouldIntervene` / `guardSnapshot` / `tracePlan` 七个符号
在 `eval_smoke_test.go` 里出现次数**均为 0**，题目数 20。

单测侧并不空：v2.3 相关单测合计 **99 项**（envreq 17、restore_drill 10、budget 8、
replan 9、trace_phase 15、scope 19、ai_dbquery 6、memory 15）。

### 为什么"单测 99 项"不能替代冒烟集

两者回答的不是同一个问题：

| | 单测 | 冒烟集 |
|---|---|---|
| 回答 | 这个函数在给定输入下返回什么 | 这项能力**对外承诺**是否成立 |
| 例子 | `checkGoReq` 遇到低版本返回 `too_low` | 用户看到的是"够用/不够/未声明"三态，不会把没检查到说成检查通过 |
| 失败含义 | 实现细节变了 | 能力对外缩水了 |

**把单测通过率当能力验证，是评测最容易自欺的地方。**
v2.1 基线自己写过这条（§六.4「冒烟集不产生百分比」），本版是它的反面：
单测的**数量**同样不能替代冒烟集。

### 本版做了什么

1. 冒烟集 S01~S20 → **S01~S32**，新增 12 题覆盖 v2.3 九项交付
2. 产出本报告，重估八项指标的可测性档位

**本版仍不产生任何百分比。** 32 题全是确定性断言，冒烟集回答"能力是否正确"，
不回答"成功率是多少"。经验增益 A/B 需要真实模型调用，属v2.4 的事（见第六节）。

### 本轮补题抓到的四个问题（全部是我写断言写错，不是产品缺陷）

补 benchmark 最大的风险是**为了让它过而改断言**。本轮四次 FAIL 全部查到了根因，
没有一处是"改断言糊过去"：

**① S28 我以为所有只读语句都自动补 LIMIT。**
实际 `dbbrowse.go:205` 显式排除 `show`/`desc`/`describe` —— 这三类返回元数据，
补 LIMIT 会让 MySQL 报语法错。**实现是对的，我的断言笼统了。**
改为分开断言：`SELECT`/`EXPLAIN` 必须补，元数据类不补且必须放行。

**② S26 我在循环外调`observe`。**
`observe` 的判定是"本次调用后 productive >= max"（`plan.go:173`），
所以 max=4 时**第 4 次调用就提额**了，我在循环外再调一次自然拿到 false。
改为在循环内接住提额。

**③ S27 我以为 `stuckTools` 是死字段。**
grep 后确认 `ai_loop.go:730` 在真链路里写入——**职责是分离的**：
`shouldIntervene` 只判断，标记由调用方在真正插入引导后写。
我的测试直接调判断函数而没模拟那次写入，等于测"没人标记就重复提示"。
补上 `r.stuckTools[key] = true` 后通过。

**④ S21 我把"未安装"和"未声明"混为一谈。**
题目原本强制所有组件都是 `undeclared`，但测试机上版本探测不到 Go 时
会返回 `not_installed`（另一个真问题）。**这道题在装了 Go / 没装 Go 的机器上
表现会不同** —— 这本身就是设计缺陷：评测题不该依赖环境。
改为只断言"绝不报 ok"，并用显式构造的 `EnvReq` 列表验证摘要措辞。

**第④条的教训值得单独记**：评测题依赖执行环境是个隐蔽的坑，
它不会立刻 FAIL，只会在别的机器上变成假绿或假红。
补题时应优先用**显式输入**驱动被测函数，而不是走会探测环境的入口。

八项指标当前档位：🟢 = 经验增益 / 安全违规率 / 验证准确性 / 无效操作次数 / 误拒率；
🔴 = 任务成功率 / 首次成功率 / 故障恢复率（后三项需Ground Truth 与异常注入器）。

### 三点必须说清

**1. 经验增益已在 v2.4 测出正增益，但样本量只够看方向。**
真实调用 12 次（2 题 × 3 次 × 2 组）：T01 探索轮数中位数 **4 → 2**、
耗时 **8.6s → 5.3s**。工具序列形态也变了——A 组反复 `search_files`，
B 组直接 `read_file`。标🟢 的依据是"分子分母都能算且已有实测数"，
**不是"结论永久为正"**：后续题集扩大后数字可能变化甚至再出现负增益。

**2. 四项升🟢 的依据是"分母算得出"，不是"已经跑出数了"。**
安全违规率与误拒率升档，是因为 v2.2 记的阻塞理由（"分母需跨会话聚合"）
已被 `trace_id` 贯通审计解决。**但本版没有真实运行样本，
这两项指标目前仍然没有数**。档位说的是"现在能算"，不是"已经算过"。
下一版若仍拿不出数，就该按口径 §五的规则处理指标回退。

**3. 本版冒烟集仍不产生任何百分比。**
32 题全绿只说明"能力正确"，不是"成功率 100%"。这条纪律从 v2.1 沿用至今。

## 五、这一版补题得到的教训

1. **单测数量不能替代冒烟集。** v2.3 有 99 项相关单测，冒烟集却一题未加——
   结果是九项能力从未被端到端验证过。单测证明实现正确，
   冒烟集证明能力对外成立。

2. **评测题不该依赖执行环境。** S21 第一次跑就因为"测试机上探测不到 Go"
   而 FAIL。若不是逐题查根因，很可能直接把断言改成"接受 not_installed"，
   那道题从此在装了 Go 的机器上变成假绿。**优先用显式输入驱动被测函数。**

3. **断言失败时先查实现，再查断言。** 本轮四次 FAIL 全是我写错。
   实现侧最值得注意的两处：`dbReadOnlySQL` 对元数据语句不补 LIMIT（正确设计）、
   `observe` 在第 4 次调用就提额（不是循环外）。**改断言前必须读到实现。**

4. **"这个字段是不是死的"要grep 到底。** S27 我以为 `stuckTools` 从未被写入，
   差点当成产品缺陷记进基线。grep 发现 `ai_loop.go:730` 有写入，
   只是职责分离（判断与标记分开）。**误判缺陷比漏判更坏**——
   它会被写进报告，后人以它为依据做决策。

5. **档位纪律要对自己也生效。** 经验增益这版从 🔴 升到 🟡 是有依据的
   （Memory 层交付了），但绝不能升到 🟢。上一版立的规矩这一版差点自己破。

### A/B 的关键发现（本轮最重要的方法论）

**「开关切了」不等于「有东西注入」。**
第一版 A/B 跑出"两组全0、增益 0.000"，
根因是 `memories.json` **一条都没有** —— B 组虽然开了记忆，
但 `memoriesFor()` 按关键词匹配不到任何内容，注入量为零。
预置一条真经验后立刻测出 4 轮 → 2 轮的清晰增益。

**任何"两组的观测量都等于默认值"的结果，都必须先怀疑采集链路或注入链路坏了，
而不是先下"无影响"的结论。** 已把这道防线写进 `tools/ab_memory.py` 的 `chat()`。

### 关于 A/B 的前置条件（本轮核实）

**真实轨迹样本不够，必须主动造任务跑。**
`trace-20261004.jsonl` 共 42 条，但最近一条是：
```json
{"actor":"ai","outcome":"aborted","verified":false,"steps":[]}
```
**`steps` 为空。** 靠回头统计已有轨迹算不出经验增益。

`eval/fixtures/` 下已有 4 个可复现样本（frontend-npm-dev / frontend-serve /
frontend-dangerous-only / backend-cmd-layout），可直接作为 A/B 的任务集载体。
`smokeCfg` 这个 helper 已经演示了怎么在测试里切 `MemoryEnabled`——
A/B 两侧的配置隔离有现成模式可循。
