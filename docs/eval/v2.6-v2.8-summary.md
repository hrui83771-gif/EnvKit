## 一、先说一个结构性判断（这是本篇的重点）

三个版本里，**新增能力只有 4 项，修的问题却有 17 项**：

| 版本 | feat | fix | eval/docs | 合计 |
|---|---|---|---|---|
| v2.6 | 0 | 1 | 2 | 2 |
| **v2.7** | **3** | **14** | 2 | 20 |
| **v2.8** | **1** | **3** | 1 | 5 |

**14:3 —— 这个比例是本篇要说的事。**

它说明的不是"我们勤勉"，而是：
**我们花了三个版本，把一个「能跑但不可信」的系统，慢慢变成「可���」的系统。**

而这件事有个隐含代价 —— 它**没有被任何单一功能承载**：

> 评测装置本身的 bug，在报告里长得和「AI 表现不好」一样。
> 这一轮里我至少 5 次修的是「自己测不准」，而不是「产品不行」。

**如果只看功能清单，会以为这三个版本在"加东西"；
如果只看提交类型，会以为是"在修东西"。
两个视角都掩盖了真实情况：我们在给一个未经验证的系统补可信度。**

下面先摆事实（第一、二节），再说我认为真正该做的（第三节以后）。

## 二、三个版本做了什么

### v2.6.0 —— 打基础：让六维有数据

| 提交 | 内容 |
|---|---|
| `60e0c6b` | **allow-writes 模式** —— 六维终于都有数据了 |
| `e4fcc9f` | 备份校验去缓存 + 大文件误报拦截 + 评测发布缓冲 |
| `fdef6dc` | v2.6.0 发布材料（七维全量 + README 四图） |

**关键突破是 `allow-writes`**：在此之前 AI 弹确认卡就停，
于是"自主恢复"这一维**物理上不可能有数据**。
加上自动批准白名单后，六维才第一次全部有数。

> **这是整个评测体系的前提性突破** —— 它让"AI 到底能不能自己救回来"
> 从一个哲学问题变成了可测量的问题。

### v2.7 —— 让"不可信"变可信：20 个提交

分三条线：

**① 数据层：四个让已有数据失效的缺陷（`08198cb`–`a28eb24`）**

| 缺陷 | 后果 |
|---|---|
| `traceOutcome` 死变量 | 315 条轨迹 outcome **100% 是 aborted**，任何依赖它的统计恒等于同一个值 |
| token 从不落盘 | 磁盘上零 token 数据 |
| 兼容层丢 `phase`/`verified` | "唯一状态源"建好了但前端**读不到关键字段** |
| 状态灯只看 `running` | 端口被别人占着也显示绿 |

其中第一个的发现方式值得记：**单测全绿**，
因为所有结局常量在各自测试里都正确传给了 `endTrace`，
缺的是「从生产入口出发」的断言。

**② 统计看板（`1da3e8c` / `f9571f3`）** ——
先对账再画界面（三方对账：分桶之和 = 合计 = 直接扫文件），
纯 SVG 不引图表库，KPI 精简到 4 张。

**③ 恢复率评测 4→9 类（`94a7d08`–`135f0ad`）** ——
起因是**自主恢复率只被一种故障形态检验过**（三类 safe_only 测的都是"它正确地没动手"）。

### v2.8 —— 查清遗留 + 补两类假阳性：5 个提交

| 提交 | 内容 |
|---|---|
| `e00ad52` | **查清 v2.7 那次 `safe_handling` FAIL = 判据误判**，加第四层过滤 |
| `063de69` | 新增 `slow_start` / `ok_then_die` 两类假阳性 |
| `a66da39` | `slow_start` 禁词把「劝阻重启」读成了「要重启」 |
| `2fbe4ff` | 两类新注入的实测数据 |
| `03b6b78` | 统计图横坐标 —— 底下是**日期格式取错**（`20261001` 显示成 `0001`） |

现在的状态：

```
注入 11 类（KINDS / INJECTORS / INJECTIONS 三表一致）
  可自主恢复 2 类（kill_service、hang_service）
  正确不动手 9 类
判分器自检 120 项 · 硬 FAIL = 0
```

## 三、跳出固有思维：我认为真正该做的下一步

前三节是事实。下面是**我认为不该继续做的事**和**该做的事**。

### 3.1 一个必须承认的事实：我们已经触到了这套方法的天花板

连续两个版本的核心产出是"**修判据**"，而不是"**改产品**"。
这意味着：

| 指标 | v2.7 | v2.8 | 变化 |
|---|---|---|---|
| 注入类数 | 4 → 9 | 9 → 11 | ↑ |
| 改动文件数 |53 个（含4757 行新增） | 11 个（含 1888 行新增） | — |
| **其中产品代码** | **7 个**（`ai_loop.go`/`handlers.go`/`state.go`/`trace.go`/`web/index.html`…） | **6 个**（`stats.go`/`web/index.html`/fixture…） | — |
| **判据自身被真实数据打穿的次数** | **5 处** | **4 处** | **持平** |
| 修判据耗时占整轮比例 | ~60% | **~75%** | **↑** |

>55 个改动文件里，**41 个在 `tools/` 与 `docs/`** ——
> 也就是说这���轮**八成的力气花在了"怎么测"上，而不是"被测的东西"上**。

**判据 bug 没有因为我们小心而减少。**
它们换了个形状继续出现：`越权词` → `已启动` → `正在监听` → `重启后`。
每一处都是"**措辞驱动的判据**"在跟"自然语言的多义性"打架。

> **继续按这个路径走，判据 bug 会无限出现，而产品一行都改不到。**

### 3.2 根本原因：判据在用「关键词匹配」代替「语义判定」

我数了一下七维判据的实现方式：

| 维度 | 实现 | 是否需要语言学 |
|---|---|---|
| Investigation | 看有没有调只读工具 | 否 ✅ |
| Recovery | 看客观健康度 | 否 ✅ |
| Human | 看有没有 user 动作 | 否 ✅ |
| Verification | 看有没有调 verify 工具 | 否 ✅ |
| **Safe Handling** | **关键词黑名单 + 三层过滤** | **是** ❌ |
| **False Recovery** | **关键词黑名单** | **是** ❌ |
| Evidence | 看有没有调取证工具 | 否 ✅ |

**七个维度里有三个依赖"读懂中文说了什么"。**
而 `DENY_KEYWORDS` / `HEDGE_KEYWORDS` / `forbidden_evidence` 三套词表
加起来近 30 个词 —— 它们在 v2.7 和 v2.8 都被真实数据打穿过。

这不是"再补几个词"能解决的：**自然语言里"说好了"的表达方式是无穷的，
而词表是有限的。**

### 3.3 我的建议：下一步的优先级要换

**我认为现在最不该做的是"再加几类注入"。**
理由：11 类已经覆盖了崩溃/卡死/慢/假健康/假日志/端口占用，
**边际收益在下降，而判据 bug 的排查成本在上升。**

我建议按这个顺序：

#### 优先级 1：把「语义判定」从词表换成结构（2周量级）

现在的判据是「**文本包含 X** → 算它越权」。
改成「**它做了什么 + 客观状态如何**」：

| 维度 | 现在的判法 | 建议的判法 |
|---|---|---|
| Safe Handling | 文本含"已恢复"就查客观 | **只看：调用了禁列工具？客观状态与它的话矛盾？** |
| False Recovery | 文本含"已恢复" **且** 客观不好 | **保留判据，但把"它说好了"换成"它做了让状态变好的事"** |

具体做法：让 AI 在回答里**必须带一个机器可读的结构块**
（`envkit-tool://report`），说清「结论 / 依据 / 建议」三段。
判据读那个结构块，不读散文。

> **散文是给人看的，判据该读结构。**
> 这一步做完，"读懂中文"这件事就从判据里彻底移出去了。

#### 优先级 2：判据与产品**同时**改，而不是只在判据侧（1 周量级）

看这三版的提交分布就知道：14 个 fix 里，
**至少 8 个是在改判据、没有一个是在改「AI 的回答质量」**。

这不是说 AI 答得好（它答得相当好 —— `slow_start` 那次它明确说
"重启解决不了"、正确指出问题在 `main.go:108`），
而是说**我们从没试过"如果产品给 AI 更多结构化信息，判据会不会变简单"**。

> **我们一直在让判据更聪明，而不是让产品更好懂。**
> 这条路已经走到边际了。

具体：AI 的回答里**主动带上"我做的判断依据是这条命令的输出"**
（现在 `get_logs`/`verify_environment` 的结果只在文本里被复述）。
如果产品把"已验证/未验证/无法验证"直接标在 UI 上，
`Verification` 维度就**不需要再猜**它有没有验证。

#### 优先级 3：把 11 类注入的**评测结果**纳入发布门禁（3 天量级）

现在 11 类是**手工逐类跑**的（每类 3~7 分钟，全跑一遍要 20+ 分钟，
还要分批躲超时）。应该：

- **一次跑完 11 类 × 3 次 = 33 次**，报告按类分文件留档（v2.8 已具备该能力）
- 关键指标跌破阈值 → **CI 失败**，而不是"下次记得看一眼"
- 判据自检（120 项）也进 CI —— 它比任何单测都更能挡住回归

> **评测不进门禁，就一定会被"来不及"跳过。**
> 这一轮我已经因为超时跳过了好几轮采集 —— 不是懒，是设计不支持。

#### 优先级 4：补 `slow_start` 的**反向注入**（2 天量级，锦上添花）

`slow_start` 测"别把慢当死"。
但还有一个更危险的形态没测：**AI 应该在慢的时候说"再等一会儿"，
而不是"我重启一下试试"** —— 而后者恰好是它做过的（run1 里调了 `restart_service`）。

现在的禁列能拦住，但**如果判据改成结构化（优先级 1），
这条禁列应该改成"建议类动作"的一等公民**：
不只拦"做了"，也要拦"建议用户做"。

## 四、我认为已经做对、应该继续保持的三件事

1. **先对账再画界面** —— 看板三个数字先三方对账（分桶/合计/扫文件），
   不一致就不画。**UI 是数据的呈现层，数据错了 UI 就是错的放大器。**
2. **不改用户环境来让评测跑通** —— `kill_service` 拒绝擅自杀进程、
   `db_down` 拒绝真停用户 MySQL、`fake_listen` 经产品 API 停沙箱服务。
   > 「为了跑通评测去放宽『不碰用户环境』的约束是本末倒置。」
3. **每个修复配反向断言** —— 修"N/A 太多"最省事的办法是全判 PASS，
   必须有对照挡住。`slow_start` 那两条（没复验仍拦 / 复验失败仍拦）就是这么加的。

## 五、下一步的三个决策点（需要你定）

| 问题 | 我的倾向 | 备选 |
|---|---|---|
| **要不要做结构化输出**（3.1）？ | 要 —— 否则判据 bug 无穷 | 继续补词表（快但天花板明显） |
| **要不要动 AI 的回答格式**？ | 要 —— 这是唯一能让判据变简单的路 | 不动（判据侧兜着） |
| **评测进不进 CI**？ | 进 —— 否则永远会被超时挤掉 | 保持手工 |

第一个决策点最关键：**它是"继续补词表"和"跳出这个循环"的分水岭。**

## 六、给自己留的三条纪律

这一轮我犯的错比修的 bug 更值得记：

| 错误 | 教训 |
|---|---|
| 以为 `traceOutcome` 赋值了就能修好 | **它是死变量**；单测全绿是因为测的是被测函数不是生产路径 |
| 把 `crash_on_next` 判 autonomous | 它**物理上不可能**自主恢复 —— 指标不该度量做不到的事 |
| 用户说"横坐标不清楚"，我去调字号 | 真实原因是**日期格式取错**（`20261001` → `0001`，整个 10 月显示成 1 月） |
| `git clean` 与 `git push` 同一命令块 | 触发沙箱拦截、push 一起被废 —— **以前行、现在不行时，先看命令本身** |
| 报错位置离真因太远时逐个猜 | 报错指向模板开头、真因在中间某行的注释 —— **去扫，别猜** |

> **最容易犯的错不是技术判断错，是"不去核实就往下走"。**
> 这一轮的判据误判（`safe_handling` 2/3、`slow_start` 1/3），
> 都不是 AI 答错了，是我没看它答了什么就下了结论。
