## 二、冒烟集暴露的实测问题

### 2.1 一个真实 bug（已修）

**症状**：S05 首次运行失败，`blocked=[]`——被拒脚本没有报给用户。

**根因**：`eval/fixtures/frontend-dangerous-only/package.json` 的 `comment` 字段值里有
未转义的英文双引号（`挑一个"最不像的"`），导致整个 JSON 解析失败，
`parsePackageJSON` 静默返回空 → 推断层看不到任何脚本 → 报"无脚本"而非"全是危险脚本"。

**暴露出的真问题**：不是 fixture 本身，而是 **`parsePackageJSON` 解析失败时没有任何日志**。
这与 v2.0 修过的"AI 谎报"是同一类问题——**失败被静默吞掉，上层以为"没有这个信息"，
于是给出错误但看似合理的结论**。

**处置**：
- 立即修了 fixture
- **记入 v2.2 待办**：`parsePackageJSON` 与 `readPackageScripts` 解析失败时必须
  区分"文件不存在"与"文件存在但解析失败"，后者要 warn 级留痕。
  推断层更不能把"解析失败"与"没有该字段"混为一谈。

### 2.2 ID 命名规范问题（已修）

`explore_smoke_test.go` 初版误用了不存在的 `explorePathDenied`。
实际函数是 `aiSafePath`（沙箱）与 `exploreSecretPath`（敏感文件）。
**写测试时不能猜函数名，要先 Grep 核实。**

## 四、基线结论：v2.2 优先级由此确定

原计划 v2.2 的交付项是「Plan + PolicyGate + 状态机 + 健康检查扩展」。
基线数据显示，**其中 PolicyGate 与 Trace 的优先级应该提到最前**，理由：

1. **三项指标卡在 PolicyGate**（安全违规率、误拒率、以及"什么算危险"的唯一定义）；
   不做它，v2.2 交付了 Plan 层也无法证明安全性。
2. **两项指标卡在 Trace**（无效操作次数、验证准确性）；
   没有任务轨迹，"AI 是不是在瞎试"永远无法回答。
3. Plan 层依赖 PolicyGate 存在（步骤要能被判定档位），**顺序上 PolicyGate 必须先行**。

### 调整后的 v2.2 顺序

| 序 | 交付项 | 理由 |
|---|---|---|
| 1 | **PolicyGate 四档 + 判定日志** | 解锁 3 项指标；Plan 的前置依赖 |
| 2 | **Trace 最小版 + `trace_id` 贯通审计** | 解锁 2 项指标；是"无效操作"与"验证准确性"的数据源 |
| 3 | 进程生命周期验证（存活/崩溃/漂移） | 补 🔴 缺口；验证准确性的基础 |
| 4 | `/api/runtime/state` 唯一状态源 | UI 重构的前置 |
| 5 | 服务状态机 | 状态源的数据模型 |
| 6 | Plan + Re-plan | 依赖 PolicyGate，故排后 |
| 7 | 备份可还原性深度验证 | 独立交付，不阻塞前面 |
| 8 | `ai_loop.go` 拆分 | 与 Plan 改动同批做，避免二次动同一文件 |

## 五、这次基线的方法论教训

1. **fixture 必须是固定的磁盘文件**，不能临时构造。临时样本会随代码一起变，
   基线数据就失去可比性。
2. **"静默失败"是最危险的失败模式**。本轮 S05 失败暴露的 fixture JSON 解析问题，
   根因是 `parsePackageJSON` 解析失败不报错——上层无法区分"没有"和"读不出来"，
   于是给出了错误结论。这与 v2.0 修的"AI 谎报成功"同源。
3. **写测试不能猜函数名**。`explorePathDenied` 是我凭印象写的，实际不存在。
4. **离线能测的和需要真实环境的要分开**。本轮基线只能覆盖"决策正确性"，
   覆盖不了"执行与验证正确性"——后者必须等 Trace 与执行器。
   把"不可测"明确写进报告，比凑一堆好看的数字更有价值。
