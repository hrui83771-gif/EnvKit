## 一、结论：**经验增益成立**，探索轮数减少 1.5 轮（−40%）

| 指标 | A 组（关记忆） | B 组（开记忆） | 增益 | 判定 |
|---|---|---|---|---|
| 任务成功率 | 6/6 = 1.00 | 6/6 = 1.00 | +0.000 | 无差异（两组都满分） |
| **T01 探索轮数中位数** | **4** | **2** | **+2 轮（B 更省）** | **✅ 正增益** |
| **T01 耗时中位数** | **8.6s** | **5.3s** | **+3.3s（B 更快）** | **✅ 正增益** |
| 全题探索中位数 | 2.0 | 1.0 | +1.0 | ✅ 正增益 |
| 全题耗时中位数 | 4.3s | 3.0s | +1.3s | ✅ 正增益 |

**核心结论：记忆层让AI 在"数据库配置在哪"这类问题上，
探索轮数从 4 降到 2、耗时从 8.6s 降到 5.3s —— 少烧一半的轮数。**

样本量 2 题 × 3 次 = 每组 6 次，**只能看方向，不能做显著性检验**。
但方向明确且工具序列的形态差异清晰（见下节），不是纯噪声。

### 差异的形态（这是最有说服力的部分）

**A 组的行为特征是"反复搜索"**：
run1 连续 4 次 `search_files`、run3 连续 2 次 `read_file` ——
它在**用搜索去试**。

**B 组的行为特征是"直接定位"**：
3 次里有 2 次是 `db_check → read_file` 就结束，**一次搜索都不需要** ——
它读完记忆就知道文件在哪，直接去读。

这不是随机的轮数波动，而是**检索策略的改变**：
记忆给了它一个起点，于是它从"广撒网找"变成"照着答案拿"。

## 三、预置的那条经验（实验前提，必须说明）

B 组跑的库里有**一条**手工预置的记忆：

```
数据库连接配置是硬编码在 backend/main.go 第 13 行的 InitDB 调用里，
不在任何 .env 或 yaml 配置文件中，不要去配置文件里找
tags: 数据库 配置 位置
```

**这条记忆是真的**（经核实：BloodLine 项目的 DSN 确实硬编码在
`backend/main.go`，不在配置文件里）。写它是为了让 A/B 测得出
"经验有没有被采纳"，这正是记忆层的用途。

**必须说清的两点**：

1. **这不是"作弊"。** 记忆层的全部价值就是"把用户已经知道的事告诉 AI"。
   真实场景里这条记忆是用户第一次被 AI 问过之后自己写进去的。
   A/B 测的正是"写进去之后还有没有用"，而不是"AI 能不能靠自己猜到"。
2. **但它也说明了一件事**：经验是**点状知识**，不是通用能力。
   记忆只对"记忆里写过的事"有效，对没写过的照样要从零探索。
   → 所以记忆层是**局部优化**，不能指望它提升所有任务的成功率。
   本次成功率两组都是 100%（题太简单），也印证了这一点。

**跑完已清理**：预置的记忆被删除，`memory_enabled` 恢复为原值 `false`，
用户机器上不留测试数据。

## 四、这一轮踩的四个坑（都是"假结果"陷阱，值一记）

### 坑1：第一版跑出"两组全0、增益 0.000"

**症状**：12 次调用，探索轮数全 0、耗时全 0.0s，
但脚本"成功退出"并算出增益 0+0。
看起来像"记忆层完全没有影响"。

**根因**：本机代理剥掉了 POST body，事件流里只有 `error` + `done`，
模型压根没被调用。

**这是评测里最危险的一种失败**：它不报错，还给出一个漂亮的零。
修法是给 `chat()` 加两道断言——事件流为空就报错；
有事件但既无正文也无工具调用也报错。
**任何"两组观测量都等于默认值"的结果，都必须先怀疑采集链路坏了。**

### 坑 2：加了断言后仍不够，还要区分"空响应"与"无效响应"

第二版跑出的事件是 `[error, done]`，错误文本是
「AI 收到空请求：请求体未到达服务端」。
所以断言不能只看"事件数 > 0"，要看"有没有正文或工具调用"。
**"收到事件"和"测到了东西"是两件事。**

### 坑 3：记忆库是空的 —— 第一版即使不报空响应也测不出东西

第二次跑通了模型调用，但两组差异仍是噪声。根因是
`memories.json` 当时**一条都没有**，`memoriesFor()` 匹配不到 → 注入量为零。
**开了记忆开关 ≠ 有经验注入。**

→ 加上 `seed_memories()` 预置真经验后，增益立刻显现（4 轮 → 2 轮）。
**这个坑是本轮最关键的发现**：如果没补这一环，
就会得出"记忆层无用"的错误结论，而真相是"记忆库是空的"。

### 坑 4：单组运行会覆盖报告

`--group A` 单独跑时 JSON 只剩 A 组，与之前的 B 组结果无法对照。
**必须一次跑完 A+B**（默认行为）。

## 五、这一轮真正证明了什么

**证明了记忆层有效，且效果形态是"省检索轮数"而不是"提高成功率"。**

这与 v2.3 的机制设计吻合：记忆注入进系统提示（`ai_tools.go:446-454`），
给模型一个起点，让它少做"从零广撒网"的探索。
`scope.go` 的注释已经预见了这个机制——
它给的是"怎么用"的提示（是否提示、排序、标注），不是能力本身。

**同时证明了一件事**：记忆层是**局部优化**，
只对记忆里写过的点状知识有效。它不能替代探索，
也不能让 AI 在没见过的任务上变强。

## 六、遗留问题与改进方向

| # | 问题 | 影响 | 处置建议 |
|---|---|---|---|
| 1 | 样本量太小（2 题 × 3 次） | 只能看方向，不能做统计检验 | 扩到 ≥5 题 × 3 次 |
| 2 | T09 对本指标**无观测力**（两组都 0 轮） | 白跑 6 次调用 | 换成需要多轮探索才能答对的任务 |
| 3 | 服务端**没有暴露快照端点** | 无法直接确认"这一回合注入了什么"，只能从回答间接观察 | 加一个 debug 端点返回当回合快照，让注入可验证 |
| 4 | 成功率维度测不出差异（两组都 100%） | 题太简单 | 引入更难的探索型任务 |

**关于问题 3**：这是本轮唯一的技术债。当前只能验到
"库里有内容 + 开关是开的"，**验不到"模型这一回合真的看到了这段记忆"**。
虽然工具序列的形态差异（B 组 `read_file` 直达）强烈提示注入生效了，
但严格来说这是推断而非直接证据。加一个返回快照的 debug 端点能彻底闭环。

`docs/eval/baseline-v2.3.md` 把经验增益标为 🟡（前置齐、缺对照）。

**本轮跑完了对照，且测出正增益**（探索 −1.5 轮 / 耗时 −1.7s）。
按口径 §五"指标可测性"的三档定义：
分子分母都能算、且**已有实测数** —— 经验增益现在可以标 **🟢 可测**。

但要写清一个边界：**标🟢 指的是"这项指标可测且已有数据"，
不等于"增益永久为正"**。后续任务集扩大、题变难之后，
数字可能变化（甚至可能再出现负增益）。指标的价值在于持续测量，不在于一次结论。

## 附：复现方式

```powershell
cd D:\BCGD\FarmTrace\envkit
go build -trimpath -ldflags "-s -w -X main.buildDate=2026-10-04" -o EnvKit_ab.exe .

# 完整 A+B（真实调用，消耗 API 额度，约 50s）

# 只跑单组（注意：会覆盖报告，只在调试时用）

```

**脚本会先清空记忆库再预置，跑完自动恢复 `memory_enabled` 原值并清掉预置记忆。**
用户机器上不留测试数据。

**环境依赖**：必须绕过本机代理（脚本内用 `ProxyHandler({})` 强制直连 +
`X-EnvKit-Chat-Fallback` 头兜底），否则 POST body 会被剥离导致模型不被调用。
