v3.0 布局：设计说明

原型用真实字段与真实数据渲染，非静态图。数据取自本机实测。

1. 这份布局解决的核心问题

v2.2 已经交付了统一状态源 /api/runtime/state，但 前端一次都没接——它在 web/index.html 里出现 0 次，issues 被引用 0 次。 前端仍在用三套轮询自己算状态。所以 v3.0 第一批工作不是改版式，是把已交付但闲置的能力接上。

2. 绿灯必须以 verified 为条件

试试顶部的「按旧规则上色」开关。切过去后后端会变绿——但它的 phase 是 degraded（runtime.go:52 的定义： 「进程在但未通过复验」）。

如果只按 running 上色，前面所有验证层的努力在视觉上等于零： 用户看到绿灯，AI 说已启动，实际上从没验过。这与链端判据、守护状态是同一条纪律—— 不确定时显示"未验证"，不显示"正常"。

3. 问题区每条必须带出路

Issue.Action 是后端算好的可执行下一步。前端丢掉它， 等于把「该干什么」的负担推回给用户——而给不出下一步的告警等于噪音。 所以每条都必须渲染 action，并带一个跳到对应工作区的入口。

4. 入口数量没变，但不再一屏铺开

6 个顶层面板 → 6 个工作区。变化在于每个工作区内部按任务分组： 「诊断」里的健康检查、链端、守护、日志是四件不同的事，不该平铺在一个页面里。

「设置」四组默认全部折叠——配置是"改一次用很久"的操作。 如果你实际是天天改配置，这一条该反过来，说一声我调。

5. 手动驾驶权

  • 首页按钮直连服务端，不经过 AI、不依赖记忆开关
  • 手动操作后立即刷新状态，不等下一个轮询周期
  • AI 未配置 / 未启用 / 密钥失效时，本页全部功能照常
  • 手动与 AI 的操作在审计里 actor 区分，结构一致

6. 布局未定死的部分

卡片的具体尺寸、栅格断点、折叠默认态、问题区最多显示几条—— 这些要看真实使用反馈再定，不在设计稿里锁死。
